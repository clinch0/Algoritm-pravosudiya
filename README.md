# Второе мнение

Локальное рабочее пространство для учебного юридического дела: проекты, документы, постоянный словарь замен, поиск норм, локальная LLM и объяснимые формальные проверки наказания. Проект конкурса «Алгоритм правосудия. Второе мнение».

**Это исследовательский прототип.** Используйте синтетические документы. Вывод модели не является судебным решением; найденная ссылка не доказывает правильность каждого утверждения. Обфускация уменьшает раскрытие данных, но не освобождает от требований 152-ФЗ.

## Запуск на Windows

1. Установите Python 3.12. Запустите `setup.bat` для создания окружения и установки зафиксированных зависимостей.
2. Запустите `run.bat`, откройте http://127.0.0.1:8000 . Демо-вход: `demo` / `demo123`.
3. Создайте проект, загрузите TXT, DOCX или PDF с текстовым слоем. Во вкладке «Словарь замен» проверьте найденные значения, добавьте пропущенные и варианты имени.
4. Напишите вопрос, нажмите «Подготовить запрос», проверьте JSON, подтвердите просмотр и отправьте.
5. Без настроенной модели система только подготавливает контекст. Для реального ответа настройте локальную LLM ниже.

Остановка — Ctrl+C в окне сервера. Файлы БД и ключа в `data/` сохраняются. Не удаляйте ключ: без него зашифрованные документы не восстановить. Для переноса дел остановите сервер и сохраните закрытую копию каталога данных; Windows DPAPI привязывает ключ к учётной записи ОС, простое копирование на другой компьютер недостаточно.

## Локальная LLM: Ollama или LM Studio

Для Ollama установите приложение, выполните `ollama pull qwen3:4b`. Это начальная небольшая модель для проверки связки, а не подтверждённый юридический эксперт. Создайте локальный `.env` в корне проекта:

```dotenv
VO_LLM_BASE_URL=http://127.0.0.1:11434/v1
VO_LLM_MODEL=qwen3:4b
VO_LLM_PROVIDER=ollama
```

Перезапустите backend. Для LM Studio загрузите локальную модель, запустите Local Server и задайте `VO_LLM_BASE_URL=http://127.0.0.1:1234/v1`, `VO_LLM_MODEL` равным идентификатору в `/v1/models`, `VO_LLM_PROVIDER=compatible`. Модель должна поддерживать JSON mode. API-ключ, если включена локальная авторизация, задаётся только в `.env` как `VO_LLM_API_KEY`.

Адаптер разрешает loopback и `host.docker.internal`, отключает HTTP redirects и системный proxy, отклоняет идентификаторы с `cloud`. Локальный URL сам по себе не исключает облачный прокси: выберите скачанную модель, отключите облачные функции runtime и проверьте исходящий трафик перед пилотом. Ключи, модели, документы и рабочие БД в Git не добавляются.

Если Ollama сообщает `redirect target not allowed` и адрес `198.18.*`, проверьте Fake-IP/DNS режим вашего сетевого клиента. Не отключайте проверку TLS и защиту адресов. Допустим ручной импорт GGUF из официального репозитория разработчика после проверки хеша. Фактический результат подключения на машине разработчика записан в `docs/STATUS.md`.

Пример вопроса для небольшого корпуса: «Какие гарантии неприкосновенности частной жизни закреплены в Конституции?» На CPU ожидание может составлять несколько минут; ответ ограничен по длине. Система отклоняет неизвестные ссылки и служебные токены, сохраняет ответ в проекте и позволяет локальное восстановление основных значений.

## Docker Compose

Установите и запустите Docker Desktop с Linux containers. В корне проекта:

```sh
docker compose up --build -d
```

Откройте http://127.0.0.1:8080 . Проверка: `docker compose ps`; логи: `docker compose logs --tail=50 backend`; остановка: `docker compose down`.

Логические элементы — **UI, backend, БД**. В данном MVP физически два контейнера: nginx UI и Python backend; SQLite хранится в именованном томе `db_data`. Отдельный сервер БД не добавлен, поскольку один backend работает с локальным объёмом данных. Том переживает `down`/`up` и пересоздание контейнеров. **`docker compose down -v` удаляет том и данные.** Для нескольких backend-процессов/серверов следующая миграция — PostgreSQL и отдельный сервис БД.

Для модели на хосте Docker задайте в `.env` `VO_LLM_BASE_URL=http://host.docker.internal:11434/v1` и реальное имя модели. Сервер модели должен быть доступен Docker; не открывайте его всей сети без ограничения доступа. `.env.example` — образец. Для Windows-запуска через `run.bat` нужен адрес `127.0.0.1`, для контейнера — `host.docker.internal`.

Порт UI опубликован только на localhost; backend и БД наружу не публикуются. Backend запускается непривилегированным пользователем. Демо-пароль не подходит для публичного размещения.

## Как устроены документы, RAG и MCP

В каждом проекте свой словарь. Программные правила обнаруживают часть ФИО, телефонов, почты, паспортов, СНИЛС и адресов; человек дополняет словарь и объединяет варианты одной сущности. Пример заменителя: `⟦Гражданин А·a123⟧`. Короткий namespace отличает проекты; грамматическое склонение при восстановлении пока не сохраняется.

При добавлении документа/варианта пересчитываются маски и ревизия проекта. Старое подтверждение запроса становится недействительным. Перед отправкой сервер заново строит JSON из хранимых оригиналов. Модель не получает таблицу восстановления. Результат хранится зашифрованно; после изменения контекста прежний ответ не показывается как актуальный.

Нормативный RAG использует SQLite FTS5. Сейчас начальный нормативный корпус — четыре фрагмента Конституции (статьи 2, 18, 21, 23) с источником Минюста и SHA-256; применимость редакции на дату не подтверждена. Документный поиск выбирает до четырёх релевантных фрагментов уже обработанных документов, до 6000 символов суммарно. Это лексический retrieval, без embeddings; он может пропустить семантически связанные фрагменты и слишком длинные неразбитые абзацы. При отсутствии нормативных источников генерация не запускается.

Один MCP-сервер `mcp_server/server.py` предоставляет семь инструментов: `analyze_document`, `check_parameters`, `legal_reference`, `find_similar_cases`, `case_statistics`, `search_law`, `get_law_unit`; ресурс `law://unit/{unit_id}`. Пример подключения — `mcp-config.example.json`. Каталог документов ограничен; словарь и оригиналы проектов через MCP не доступны. Backend вызывает тот же модуль нормативного поиска напрямую; внешние локальные агенты обращаются к нему через MCP. Самостоятельный многоагентный оркестратор ещё не реализован.

Пополнение: подготовьте JSON по структуре `data/law_seed.json`, проверьте официальный источник, редакцию и права использования; выполните `python tools/import_law_snapshot.py путь-к-снимку.json`. Существующий ID нельзя менять: новая редакция получает новый ID. Автоматического веб-обновления и полного актуального УК пока нет. Старый справочник санкций и формальные проверки — отдельный частичный контур, доступен в интерфейсе по `/demo`.

## Разработка и проверка

Зависимости фиксирует `requirements.lock.txt`. `verify.bat` запускает регрессии, компиляцию, сверки локальных данных и MCP. Отдельно:

```sh
python -m pytest -q
python tools/smoke_mcp.py
node tests/test_browser_projection.cjs
pip install playwright==1.56.0
python -m playwright install chromium
python tools/smoke_browser.py
```

В Windows браузерный smoke использует установленный Edge; в Linux — Chromium. Тесты работают с временными синтетическими данными, не требуют LLM API-токена. Реальную модель проверяет отдельный `tools/smoke_local_llm.py` после настройки `.env`.

CI в `.github/workflows/ci.yml` включает pytest, MCP, JavaScript, Playwright, Bandit SAST и pip-audit SCA. Сбой advisory-сервиса — неполная проверка, а не отсутствие уязвимостей. DAST и промышленная сертификация пока не выполнены.

SDD — разработка от проверяемой спецификации: требования → сценарии → реализация → регрессии → отчёт. Выбран формат OpenSpec (`openspec/specs/`); CLI не установлен. Подробнее: `docs/SDD.md`. Инструкции агентам — `AGENTS.md`; совместимый вход для Claude — `CLAUDE.md`. Навыки проекта в `skills/` не устанавливаются глобально автоматически.
